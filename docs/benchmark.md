# 性能调优基准报告（W6）

> 版本：v1.0｜日期：2026-10-13
> 目标：把经典 SQL 调优原则从"背结论"落到"看计划、量化收益、识别失效边界"。
> 复现：`python etl/benchmark.py`（对账闸门任一 FAIL 退出码 1），原始证据在 docs/benchmark_plans/。

## 1. 测试环境与方法

- 引擎与数字来源：表内耗时与执行计划产出于**沙箱环境（DuckDB 1.5.6，计划文件里的路径为 `/mnt/work/staging`）**；本地复现环境为 DuckDB 1.5.5（requirements.txt 钉版）。本地重跑 7/7 闸门全过、各案例趋势一致，但绝对耗时与加速幅度随环境漂移（C2 由 7.62x 变 11.83x，C6 由 0.73x 变 1.01x，详见 §5 与 §7）
- 数据：本地仓库真实数据（非造数）
  dwd_fact_order_item 112,650 行 / dwd_fact_delivery 99,441 行 / dwd_fact_payment 103,886 行 / dws_trade_daily 616 行
- 计时：每个 SQL 先 warmup 1 次（消除页缓存与首次编译），再计时 5 次取中位数（毫秒）
- 对账闸门：每对 SQL 的结果必须一致（精确相等，或数值容差 0.011——金额保留两位小数 + 浮点求和尾差）才允许比较耗时，不一致则整案作废
- 结果文件：docs/benchmark_plans/results.json；每个 SQL 的 EXPLAIN ANALYZE 计划在 `*_naive.txt` / `*_tuned.txt`

## 2. 结果总览

| # | 场景 | 朴素 ms | 调优 ms | 加速 | 结论 |
|---| --- | ---:| ---:| ---:| --- |
| C1 | 列裁剪 SELECT * vs 必要列 | 190.19 | 68.88 | **2.76x** | 有效 |
| C2 | 粒度选表 COUNT(DISTINCT) vs COUNT(*) | 10.66 | 1.40 | **7.62x** | 有效，收益最大 |
| C3 | 先聚合后 join | 83.73 | 72.79 | 1.15x | 有效但温和 |
| C4 | 半连接 IN vs JOIN+DISTINCT | 26.37 | 19.87 | 1.33x | 有效 |
| C5 | 窗口函数 vs 相关子查询 | 6.07 | 1.22 | **4.97x** | 有效 |
| C6 | 3 次扫描 UNION（朴素）vs 条件聚合（教条推荐） | 3.38 | 4.65 | 0.73x | **反转：推荐写法反而更慢（本地复跑 1.01x 平局，环境相关）** |
| C7 | 直接 join+WHERE（朴素）vs 手动子查询先过滤 | 24.42 | 27.54 | 0.89x | **无效：两侧计划同构，差异属噪声（本地 0.98x 同判）** |

## 3. 有效案例（4 个，含计划证据）

### C2 粒度选表（收益最大，7.62x）——字典 2.4"选表要点"的性能佐证
- 朴素：`COUNT(DISTINCT order_id) FROM order_item WHERE order_status='delivered'`
- 调优：`COUNT(*) FROM delivery WHERE order_status='delivered'`
- 机制：两者结果一致（96,478），但朴素版扫 110,197 行明细并做 `count(DISTINCT #0)` 哈希去重；
  调优版在订单粒度表（一行一单）直接 COUNT(*)，零去重。DuckDB 计划里朴素版聚合耗时 0.01s 是可观测热点。
- 迁移结论：**"多少单"就用订单粒度表 COUNT(\*)，别在明细行上 COUNT(DISTINCT)**——选对与问题粒度匹配的事实表，DISTINCT 就消失了。

### C5 窗口函数 vs 相关子查询（4.97x）
- 场景：dws_trade_daily 的 7 日 GMV 移动平均。
- 朴素：相关子查询 `(SELECT AVG(t2.gmv) ... WHERE t2.full_date BETWEEN t1.full_date-6 AND t1.full_date)`。
  DuckDB 把它去相关化成 `PIECEWISE_MERGE_JOIN` + `FILTER` + `HASH_GROUP_BY`：merge join 首阶段只应用
  `t2.full_date <= t1.full_date` 半个条件，先产生**上三角全量候选对 616×617/2 = 190,036 行**（规模 O(n²)，
  与窗口天数无关），随后 FILTER 用 `>= date-6` 收敛到 4,243 行，再分组聚合。
- 调优：`AVG(gmv) OVER (ORDER BY full_date RANGE BETWEEN INTERVAL 6 DAY PRECEDING AND CURRENT ROW)`，单次扫描滑动聚合。
- 口径注意：本表有缺日期（616 行 < 730 自然日），对照两边必须统一用"最近 7 个自然日"（RANGE）才能过对账闸门；
  ADS 生产代码用的是"最近 7 个有成交日"（ROWS），语义不同，勿混。
- 迁移结论：**滑动窗口聚合一律用窗口函数**，相关子查询去相关化后首阶段会展开 O(n²) 的上三角候选对，再由 FILTER 收敛——中间量由表规模决定，远大于窗口本身。

### C1 列裁剪（2.76x）
- 朴素：`SELECT * FROM order_item`（13 列全读）；调优：只取 4 列。
- 机制（计划实证）：`SELECT *` 的 READ_PARQUET 投影含全部 13 列，扫描耗时 0.03s；调优版只解压 4 列。
  列存引擎按列块存储，少读一列就少一份解压与 I/O 带宽。
- 迁移结论：**列存（Parquet/ORC + Hive/Spark/DuckDB）下严禁 SELECT \***，列裁剪直接省 I/O。行存库此技巧不成立。

### C4 半连接（1.33x）
- 朴素：`COUNT(DISTINCT d.order_id) FROM delivery d JOIN payment p USING(order_id)`；
  调优：`COUNT(*) FROM delivery WHERE order_id IN (SELECT order_id FROM payment)`。
- 机制：朴素版 join 后 payment 一单多笔会让订单行膨胀，需 DISTINCT 去重；IN 是半连接，命中即停不膨胀、不去重。
- 迁移结论：**只判断"是否存在关联记录"时用 IN / EXISTS 半连接**，不要为了拿存在性而 join 全表再 DISTINCT。

## 4. 温和案例：C3 先聚合后 join（1.15x）

- 朴素：delivery join payment（明细 103,886 行）后按用户聚合；调优：先把 payment 按 order_id 聚成 99,440 行再 join。
- 为何温和：payment → 订单粒度的压缩率仅 4.3%（103,886 → 99,440），本数据集几乎没有一单多笔的剧烈膨胀。
  先聚合的收益来自缩小 join 输入；压缩率越高收益越大，反之像本例只有边际改善。
- 迁移结论：**先聚合后 join 的收益与压缩率成正比**。在一单多支付、一用户多事件等高膨胀场景（压缩率 10x+）收益显著；
  本数据集收益温和是数据特征，不是技巧失效。

## 5. 失效/反转案例（认知校准，比加速更重要）

### C6 3 次扫描 UNION vs 条件聚合：沙箱反转（0.73x），本地平局（1.01x）——反转不是数据集定律
- 经典教条："一次扫描 + CASE 条件聚合"优于"三次扫描 UNION"。沙箱实验结果相反：UNION 3.38ms 快于条件聚合 4.65ms（0.73x）。
- **本地复跑（Windows / DuckDB 1.5.5）反转消失**：UNION 6.43ms vs 条件聚合 6.35ms（1.01x），且各自取最小值时方向相反（naive_min 5.42 / tuned_min 6.27）——两种写法本就在同一水平线，沙箱的 0.73x 处在机器间噪声的边缘。
- 沙箱计划里可观测的机制（这部分与版本无关）：UNION 三个分支的过滤条件都被下推到 scan 层，三个状态桶互斥分担数据
  （delivered 110,197 / canceled 542 / 进行中 1,904 行；另有 7 行 unavailable 不属于任何桶，被两侧口径一致地排除），
  下游各自只做一次纯 `sum`；而 CASE 版要扫全部 112,650 行并**多带 order_status 一列**，每行做 3 次字符串分支 +
  `ELSE NULL` 产生可空向量（sum 需处理有效性掩码）。
- 结论修正：**"少扫描"在列存 + 谓词下推时代不再是绝对真理；但"反转"也不能当新教条背**——UNION vs 条件聚合
  属于必须实测的打平区，领先方向与幅度都随引擎版本、CPU、数据分布浮动。双环境数字本身就是第 6 条结论最硬的实证。

### C7 手动谓词下推：无效（0.89x，属纯噪声）
- 假设：把 `WHERE order_status='delivered'` 手动写成子查询"先过滤再 join"会更快。
- 计划实证：**两侧计划结构完全相同**。DuckDB 已自动把过滤条件下推到 delivery 扫描（96,478 行），
  并自动给 order_item 扫描注入 `order_id IN BF(order_id)` 布隆过滤器动态裁剪。手动改写没带来任何收益，
  只是平白多一层子查询；tuned 的最小值 23.26ms 反而更低，证明 24.42 vs 27.54 是运行噪声而非真实差异。
- 结论修正：**不要替优化器做它已能自动做的改写**。手动下推、手动指定 join 顺序这类"提示"
  在现代 CBO（DuckDB/Spark3/Hive 或开启 CBO 后）面前往往无效甚至帮倒忙。正确姿势是先 EXPLAIN 看优化器做了什么，
  只在它确实没下推时才介入。

## 6. 可迁移结论（面试话术）

1. **先选对表，再谈优化**（C2）：粒度匹配的事实表让 DISTINCT 消失，是本实验收益最大的一招（沙箱 7.62x / 本地 11.83x），且零风险。
2. **窗口函数消灭相关子查询**（C5）：滑动聚合用窗口函数——相关子查询去相关化后，range join 首阶段会产生 O(n²) 的上三角候选对（190,036 = 616×617/2），窗口版单次扫描滑动即可。
3. **列存下严禁 SELECT \***（C1）：列裁剪省的是真实 I/O 与解压，2.76x（本地 2.70x，方向稳定）。
4. **存在性判断用半连接**（C4）：IN / EXISTS 不膨胀结果、不去重，1.33x（本地 1.50x）。
5. **先聚合后 join 的收益看压缩率**（C3）：压缩率越高越值，本数据集 4.3% 压缩率只有边际收益。
6. **任何"调优教条"都要用 EXPLAIN ANALYZE 验证，而且要在自己的环境验证**（C6/C7）：列存 + 谓词下推会改写"少扫描"的老经验；现代优化器已能自动下推，手动改写前先确认它没替你做好。**连"反转"结论本身也是环境相关的**（C6 沙箱 0.73x / 本地 1.01x 平局）——这是 W6 最想传递的一条。

## 7. 局限与边界

- 绝对耗时（ms 级）来自沙箱环境 DuckDB 1.5.6 + 全内存数据（计划文件里的 `/mnt/work/staging` 路径即其印记），不可直接外推到 Hive/Spark 分布式或大表场景；可迁移的是**趋势与计划形态**（去重消失、窗口单扫、下推生效），不是具体毫秒数。
- **数字来源环境**：表内数字为沙箱实测；本地（Windows / DuckDB 1.5.5）复跑 7/7 对账闸门同样全过，5 个案例方向一致、幅度随环境漂移（C2 7.62x→11.83x，C3 1.15x→1.40x），C6 由 0.73x 反转变为 1.01x 平局——引用本报告结论时，幅度与个别方向须带环境出处。
- 数据量偏小（最大表 112,650 行），部分差异在更大规模会放大（如 C2/C5），部分可能被固定开销稀释。
- 每对 SQL 均通过结果一致性闸门，差异可归因于执行计划而非口径不同。
