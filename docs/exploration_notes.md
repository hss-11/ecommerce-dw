## 二、关键发现与决策

### 发现 1：reviews 表主键重复 814 条 🔴(原去重方案已经作废，见第五节补查4/5)
- **数据**：total=99,224，uniq(review_id)=98,410，差 814
- **问题**：主键唯一性被破坏，若不去重，评价数与平均分都会算错
- **决策**（09-14 修正）：**不去重**。抽查确认重复记录 order_id 不同、其余字段完全相同，
  真实主键为 `(review_id, order_id)` 组合键；`dwd_fact_review` 粒度改为
  "一行 = 一个评价对一个订单的关联"，保留全部 99,224 行
- **理由**：按 review_id 去重会丢失该评价与另一订单的关联，导致对应订单查不到评价；
  且原方案 `ORDER BY review_answer_timestamp DESC` 因时间戳完全并列，
  ROW_NUMBER 分配随机 → **结果不确定**，同一份数据两次运行可能得到不同结果
- **若必须去重的正确写法**：ORDER BY 末尾加唯一决胜字段
  `ORDER BY review_answer_timestamp DESC, order_id ASC`
- **影响范围**：`dwd_fact_review`、`ads_review_score_*` 全部评价指标

### 发现 2：customer_id 是订单维度标识，不是自然人 🔴
- **数据**：customers 表 99,441 行，uniq(customer_id)=99,441，
  uniq(customer_unique_id)=96,096，人均订单 1.0348
- **推论**：3,345 个 customer_id 属于重复的自然人；复购人群约 3.5%
- **问题**：用 customer_id 算复购率会得到恒等于 0 的错误结果
- **决策**：所有用户指标（复购率、留存、RFM、活跃用户数）一律用customer_unique_id
- **理由**：customer_id 与订单数完全相等，它标识的是"某次下单行为"而非"某个人"
- **影响范围**：`dim_customer` 主键选择、`dws_trade_user_*`、全部用户指标

### 发现 3：一个订单可含多个商品项
- **数据**：88,863 单含 1 件（78.9%），7,516 单含 2 件，最多一单含 21 件
- **问题**：orders 表无金额字段，订单金额只能从 order_items 汇总
- **决策**：'dwd_fact_order_item' 粒度定为"一行 = 一个订单中的一个商品项"
- **理由**：这是最细粒度，可向上汇总出订单级、客户级、品类级任意指标；反之则丢失明细
- **影响范围**：全部交易类指标的计算路径

### 发现 4：一个订单可有多笔支付
- **数据**：payments 103,886 行 > orders 99,441 行，多 4,445 行；
  支付方式含 voucher 5,775 笔（通常用于组合支付）
- **决策**：'dwd_fact_payment' 粒度定为"一行 = 一笔支付",与订单事实表分开建
- **理由**：若强行合并到订单粒度，会造成订单数虚增或金额重复计算
- **影响范围**：`ads_payment_*` 指标、支付方式分析

### 发现 5：geolocation 表一对多，直接 join 会膨胀 52 倍 🔴
- **数据**：1,000,163 行，仅 19,015 个唯一邮编，平均每邮编 52.6 行，最多 1,146 行
- **问题**：按邮编 join 会把订单数据复制 52 倍，GMV 虚增且**不报任何错**
- **决策**：先 GROUP BY 邮编聚合，经纬度取 AVG、城市州取MIN,得到邮编唯一的 dim_geolocation
- **理由**：该表是邮编中心点多次采样，同一邮编多条记录属正常，聚合即取中心点
- **影响范围**：`dim_geolocation`、所有地域维度分析
- **教训**：join 前必须先确认关联键在右表是否唯一，否则结果静默错误

### 发现 5-B：join 类型导致的静默数据丢失 🔴（09-14 新增）
- **数据**：修正版对账中 `matched_orders = 98,665`，而 orders 表有 99,441 行，差 776
- **错误假设**：最初判断为"776 个订单无支付记录"
- **验证结果**：补查 7 显示仅 **1 个订单无支付记录** → 假设被否定
- **真实原因**：对账 SQL 用的是内连接 `JOIN`，`matched_orders` 是两表交集；
  由于几乎所有订单都有支付记录，缺失的 776 个订单实为**在 order_items 中无商品明细**
- **性质**：收了钱但没有商品明细 → 算不出 GMV，且用 order_items JOIN orders 统计订单量时
  这 776 单会静默消失（少算 0.78%），不报任何错
- **决策**：【手敲区】待补查 9 确认状态分布后决定：
  若集中在 canceled/unavailable → 归入无效订单排除；
  若含 delivered → 列为数据质量异常并在质量门禁中持续监控
- **教训**：内连接会静默丢弃不匹配的行。算"总数"类指标前必须对比
  `COUNT(*) FROM A` 与 `COUNT(*) FROM A JOIN B`，差值就是丢失量

### 发现 5-C：全库唯一真异常 —— 已送达但无支付记录 🔴
- **数据**：补查 7（无支付订单）与补查 11（有明细无支付订单）**双向独立查询均返回 1 条**，
  指向同一订单，状态为 `delivered`
- **交叉验证**：补查 9 统计 776 单无明细，补查 10 统计 775 单有支付，
  差额 1 单 = 该异常订单（它有明细，所以不在 776 里；它无支付，所以不在 775 里）
- **性质**：货已送达、订单内容完整、却无任何支付记录。
  可能成因：全额代金券支付未入表 / 内部测试单 / 支付数据同步丢失
- **决策**：【手敲区】不删除。DWD 层加 `is_payment_missing` 标记字段，
  并纳入 W8 数据质量门禁做每日监控
- **理由**：【手敲区】单条记录金额影响可忽略，但若该数字从 1 突增至 100，
  说明支付链路故障，必须能第一时间发现。数据质量监控的价值在于持续性而非一次性检查
- **口径提醒**：这批 775 个 canceled/unavailable 订单实收 162,591.95 BRL，
  涉及真实退款。需区分三个不同指标：
  **GMV**（商品成交额）≠ **平台实收**（扣除退款）≠ **支付流水**（含后续退款的部分）



### 发现 6：金额对账检查暴露的 SQL 陷阱 🔴
- **数据**：初版检查报"8,182 条支付金额与订单金额不符"
- **问题溯源**：初版 SQL 用了 `SUM(DISTINCT price + freight_value)`，
  `DISTINCT` 会把金额恰好相同的不同商品行去重，导致订单金额被少算
- **修正方案**：先用 CTE 把两张表各自聚合到订单粒度，再 join 比对
- **真实不匹配原因**：voucher 部分抵扣、3 笔 not_defined 金额为 0、退款未体现
- **教训**：`DISTINCT` 不是解决 join 膨胀的正确手段，它是用错误掩盖错误
- **修正结果**（补查 1）：可匹配订单 98,665｜不符 380 条｜占比 0.39%｜平均差额 0.03 BRL
  → 原版误报 8,182 条，**错误率虚高 21 倍**
- **根因确认**（补查 8）：差异幅度与分期数呈单调正相关
  （完全一致组 2.92 期 → 差异<5% 组 3.50 期 → 差异5-20% 组 6.60 期 → 差异>20% 组 12.18 期）
  → **证实差异来自信用卡分期利息**，`payment_value` 为含息总额
- **GMV 口径决策**：一律用 `order_items.price + freight_value` 汇总，
  **不用** `payments.payment_value`
- **决策理由**：分期利息是金融机构收入，不属于平台成交额；
  且该偏差与分期数正相关，属**系统性偏移**而非随机噪声，
  会扭曲高客单价人群的分析结论
- **待办**：W3 用修正版 SQL 重跑此项检查，记录真实不匹配数量

## 四、探查方法论沉淀（可复用到其他项目）

1. 先看规模 → 2. 验主键唯一性 → 3. 查关联完整性（孤儿记录）→ 4. 统计空值率
→ 5. 验关联键在右表是否唯一（防 join 膨胀）→ 6. 业务合理性检查（时间逻辑、金额对账）
→ 7. 分布特征（枚举值、评分、金额）

**核心原则**：join 之前永远先确认关联键的唯一性。数据膨胀不会报错，只会静默产出错误结果。

### 方法论沉淀：本次补查的完整推理链

1. 看到异常数字（98,665 < 99,441，差 776）
2. **提出假设**：这 776 个订单没有支付记录
3. **设计验证查询**（补查 7：LEFT JOIN payments + WHERE IS NULL）
4. **数据否定假设**：只有 1 条无支付
5. **回头审查自己的 SQL**：发现用了内连接，matched_orders 是交集而非全集
6. **修正假设**：776 是"无商品明细"而非"无支付"
7. **再设计验证**（补查 9/10/11，含对称性反向检查）

**核心原则**：假设错了不可怕，不去验证就直接写进文档才可怕。
每一个"我觉得应该是……"都要有一条 SQL 去证明它。
